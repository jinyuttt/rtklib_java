# Java 版 RTKLIB 封存实录：29 个 Bug、一张精度表，和三条没走通的路

> 版本：v3.1.0（封存版） · 日期：2026-10-23
> 关键词：RTKLIB、GNSS、PPP-AR、Java、算法移植

## 为什么会有这个项目

做 GNSS 高精度解算的团队大多绕不开 RTKLIB。C 版成熟、资料多，但在 Java 服务端里直接用，通常只有两条路：JNI 包一层，或者重写。

JNI 的问题不是"能不能跑"，而是"出了问题查不动"——栈是 C 的，状态是 C 的，算法调参还得回到 C 的调试工具链里。我们选了更笨的那条：**以 RTKLIB 2.5.0 源码为唯一数值基准，按 C 文件一一映射 Java 类结构**，状态向量、协方差存储、常量定义、边界处理逐项对齐。

笨办法的代价是，C 里那些不会写进注释的隐式约定——数组每历元清零、ANTEX 的单位、频率槽位的语义——都得靠自己踩出来。29 项修复里，大部分都在补这些约定。

---

## 一、先立一条铁律：默认路径逐值一致

项目从第一天定的规矩是：**所有扩展优化项默认关闭；关闭状态下，结果必须与 C 版逐值一致。**

这条规矩后来演化成三条 Fail-Safe：

- AR 固定失败 → 回退浮点，不丢历元；
- 没有 SSR 改正 → 退化为普通 PPP，不报错退出；
- 滤波器发散 → 保留状态传播能力，不把历元直接判死。

它最大的价值不在"对齐"，而在**排错**。后面每次出现解算差异，第一步都是把扩展开关全部关掉做二分：如果默认路径能对上，问题在新逻辑；如果对不上，问题在移植本身。29 项修复中至少有 20 项是这样定位的。

封存时的实测结果如下（2D RMS 均在收敛期后统计）：

## 三、三个最隐蔽的 Bug

### 3.1 ANTEX 漏乘 1e-3：毫米被当成了米

ANTEX/NGS PCV 文件里的所有数值——PCO 和 PCV——都是**毫米**。C 版在 `rtkcmn.c` 的 `decodef()` 里统一乘 `1E-3` 转成米，`readantex()` 和 `readngspcv()` 共用这一个入口。

Java 移植时漏了这层转换，PCO/PCV 直接按米加载，数值放大了 1000 倍。后果不是"精度差一点"，而是逐卫星出现几十米的 prefit 残差，`maxinno` 把大部分观测剔除，PPP 存活率只有 17.3%。

诊断时有个很实用的切入口：**先排除电离层**。无电离层组合的码残差满足 `Pc − P1 ≈ −I1`，带符号、必为负；如果看到的是逐卫星的大正偏差，基本可以锁定在硬件延迟或天线改正上。修复后存活率回到 60.8%。

### 3.2 卫星 PCO 缺失：SP3 给的是质心坐标

SP3 精密轨道给的是卫星**质心**（COM）坐标，不是天线相位中心（APC）。C 版 `preceph.c` 的 `peph2pos(opt=1)` 内部会调 `satantoff()`，用 ANTEX 里的卫星 PCO 把质心转到相位中心，速度项不加改正。

Java 侧整块 `satantoff` 缺失。卫星径向 PCO 大约 1.5 m，这部分偏移大部分被钟差参数吸收掉了，剩下的一小截留在 U 方向，形成分米级系统差。补齐后 dU 从 +0.126 m 降到 +0.034 m。

顺便记一下 C 的分工，移植时最容易混：

| 改正项 | 作用位置 | 对应函数 |
|---|---|---|
| 卫星 PCO | 卫星位置 | `preceph.c satantoff` |
| 卫星 PCV | 观测值 | `ppp.c satantpcv` |
| 接收机 PCO + PCV | 观测值 | `rtkcmn.c antmodel` |

### 3.3 工作缓冲跨历元泄漏

C 版 `ppp.c` 的 `pppos()` 里有一行很不起眼的初始化：

```c
double exc[MAXOBS]={0};
```

每个历元重新定义、重新置零。Java 为了减少 GC，把这类工作数组预分配在 `PppWorkBuffer` 里跨历元复用。复用本身没错，错在**没有对应地清零**。

结果是一个历元被排除的卫星，`exc=1` 状态一直留着，下一个历元即使健康也被剔掉。可用卫星数进入死亡螺旋：13 → 3 → 0，PPP 直接无解。修复就是在 `pppos` 入口加一行 `Arrays.fill(exc, 0)`，静态场景的 solved 从 1/30 回到 14/30。

这条教训后来变成一条检查纪律：**凡是 C 在函数入口初始化的数组，Java 复用版本都要逐一对齐初始化点**，不能只盯着"数组长度一样"。

## 四、三条没走通的路

技术文章通常只写成功的部分，但移植项目里，**知道哪里该停**比多修一个 Bug 更重要。

### 4.1 GBM 数据集上 3F 固定率 0%

同一个 3F 实现，WUM 产品下固定率 65.7%，换成 GBM 2026 DOY288 直接掉到 0%。

排查后主导原因是候选完备性门槛：3F 路径要求参与固定的卫星满足 OSB 记录完整性，`skipOsb=15` 这个门槛在 GBM 产品上筛掉的星太多，剩余候选不足以支撑一次有效固定。

我们没有为了让数字好看去放宽门槛——那会引入假 Fix 风险。最终定性为**非回归问题**：默认路径与浮点逐值一致，7/7 配置零连带回归，记录归档，不在封存期深挖。

### 4.2 双频 IFLC 的整周平移自由度

双频 IFLC 的宽巷取整用的是"无差分 + 全星中位数对齐"。这个机制天然带一个整周平移自由度：当公共小数部分跨过 0.5 边界时，所有卫星会同时偏 ±1 周。

在 GBM 上这个平移量是 +2.2475 周，被 δ 门拦下并回退浮点；回退后的结果与纯浮点逐值一致，没有污染。这不是数据质量问题，是方法本身的数学性质——换任何产品都会复现。

所以结论很明确：**生产环境用 3F，不通过把最小固定卫星数降到 3 来硬提固定率**。降低门槛只会把"固定率 0"换成"假 Fix"。

### 4.3 EST 模式的死锁

非组合 PPP（`IONOOPT=EST`）在 C 版里有个隐含前提：`postpos.c` 会自动加载 IGS DCB 文件。Java 侧没有对应的 `readdcb` 实现。

没有 DCB，首历元相位残差就超出 `maxinno` 门限、被全部剔除；剩下的码观测独自进入卡尔曼滤波，相位偏差状态永远不更新，滤波器永久卡在初始状态——存活率为 0，而且不是"慢慢收敛"，是**结构性死锁**。

修复分两步：移植 `readdcb`（BIA/BSX/DCB 格式），再加一个 Java-only 的 robust 开关，对刚初始化的偏差/电离层状态跳过相位剔除门限。EST 存活历元从 401~509 提升到 2880/2880。

遗留问题也如实记录：卫星-only 的 OSB 产品对 EST 几乎无效，接收机码偏差没有公开产品且随映射函数变化，无法被常数偏差吸收。这部分没有在封存版里解决。

## 五、封存决策：能力冻结，接入成本压到两行

v3.1.0 是**代码封存版**：算法能力冻结，此后只接受 bug 修复，不再新增特性。

冻结的直接好处是，SSR 数据源权限到位后，接入成本已经压缩到两处：

```java
// 1. 改 Caster 地址与挂载点
NtripClient client = new NtripClient(host, port, mountpoint, username, password, listener);

// 2. 打开 PPP-RTK 路由
cfg.enablePppRtk = true;
```

底层链路——RTCM/SSR 解码 → `nav.ssr` → `SsrCorrector` → `ppprtkos`——已经贯通，并且有离线单测覆盖，不需要再动算法代码。

未来扩展方向的真实状态（不夸大）：

| 方向 | 现状 |
|---|---|
| QZSS CLAS | `CompactSsrDecoder` 已实现 MT4073 子类型 1-12 解码；缺公开 L6 二进制样本做端到端验证 |
| Galileo HAS | `HasSsrDecoder` 已实现 COMPACT-SSR（MT1~MT9）解析；互联网 IDD 帧同步与接入未实现，且无公开事后存档 |
| IMU 紧组合 | 未实现；需要扩展 EKF 状态（姿态/速度/零偏）和动力学模型，是改动最大的一块 |

## 六、给同样在做算法移植的人

1. **先立"默认路径逐值一致"的铁律**，再谈优化。它同时是验收标准和排错工具。
2. **C 的隐式初始化是最大的坑**：`{0}`、`static`、函数内局部数组，复用到 Java 都要逐项核对。
3. **单位问题优先怀疑**：ANTEX 的 mm、气压的 hPa/Pa、高度角的弧度/度，一个漏乘就是千倍或百倍误差。
4. **坐标框架要问清楚**：SP3 是质心、ANTEX 是相位中心、RINEX 参考点还有 ARP/APC 之分。
5. **失败模式要当成一等公民**：回退浮点、退化模式、保留历元，比"报错退出"有价值得多。
6. **该停就停**：把"为什么只能到这里"写清楚，比硬凑一个好看的指标更负责。

---

## 结语

29 次修复里，最难的从来不是公式推导，而是 C 与 Java 之间那些没写进注释的约定：数组什么时候清零、数值是什么单位、槽位代表哪个频率、产品里哪个字段才是真值。

公式写错了，编译器不会告诉你；约定漏了，编译器一样不会告诉你——它只会在某一天，用一个 17.3% 的存活率或者一个 0% 的固定率，安静地提醒你。
