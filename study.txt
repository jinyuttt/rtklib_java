GREAT-PVT / PRIDE PPP-AR 算法优化借鉴方案（适配 rtklib-java / 车载测绘 / 城市峡谷）
含项目现状交叉审核与落地修订

================================================================================
0. 方案总览
================================================================================

本方案基于武汉大学 GREAT-PVT、PRIDE PPP-AR 两大科研级开源软件，针对 rtklib-java
现有算法短板，结合车载移动测绘、城市峡谷高精度RTK、PPP高精度后处理三类核心场景，
完成系统化算法选型、场景边界界定、优先级规划与工程落地规范。同时结合项目现有存量
优化能力，完成交叉比对、冲突修正、优先级重排与风险整改，形成适配当前代码基线的
最终落地版本。

方案核心原则：
- 不重构现有EKF架构、不盲目引入因子图
- 严格区分RTK/PPP算法适用性
- 测绘场景可靠性优先于固定率
- 新旧算法互补兼容、杜绝功能冲突与裸奔上线
- 先RTK后PPP，两阶段独立交付

1.2 重要勘误
─────────────────────────────────────────────────────────────────────
1）GREAT-PVT 不含因子图优化：其所有模糊度固定策略、误差模型均可在标准EKF框架下
   运行，无需重构状态估计。
2）因子图、滑窗IMU紧耦合属于 GraphRTK-INS，为独立仓库，不属于 GREAT-PVT，
   当前阶段不落地。
3）本次所有P0/P1/P2优化，均为算法层升级，与FGO无关，兼容性、工程可控性极强。

1.3 业务场景约束规则
─────────────────────────────────────────────────────────────────────
1）车载测绘场景：可靠性优先，宁可不固定、不跳变，禁止假固定输出不合格厘米级成果；
   基线多为短基线（数公里内）。
2）城市峡谷场景：多路径、周跳频发、卫星断续，需强化弧段连续性、鲁棒质控、
   自适应AR策略。
3）PPP后处理场景：追求毫米级稳态精度，依赖高精度对流层、潮汐、偏差模型与
   AR智能校验。

1.4 项目存量自研优化汇总（全部保留、新旧互补）
─────────────────────────────────────────────────────────────────────

全部纳入长期维护体系：

1）enableAmbAnchor：模糊度锚固保护，稳定历史固定解，与全新Partial AR前后互补
2）enableParRefReselect：参考星重选，为弱化版子集优化，全新Partial AR实现后
   可作为兜底策略
3）enableAdaptiveQ：运动状态自适应位置过程噪声，与参数类型级噪声模型互补叠加
4）enableIggiii：观测域IGGIII抗差降权，与PRIDE弧段域残差编辑互补
5）enableSnrMedian：SNR中值参考星选择，异构接收机网络场景有价值
6）atmFrozenNsThresh：大气冻结阈值，城市峡谷少星场景刚需
7）enableIonoTropGradient：电离层+对流层梯度估计，已实现，长基线RTK必需
8）BaseStationMonitor：基站稳定性监测，工程运维刚需，与算法优化正交
9）rtklib-adjust P0/P1/P3：基线质量加权/残差提取/H矩阵提取，平差模块独有

2. RTK阶段优化方案（先行交付）

【现有优化实现模式（所有新优化必须遵循）】
─────────────────────────────────────────────────────────────────────
项目已建立成熟的"Config开关 + RtkOptimizations独立类 + RtkCore最小侵入"模式：

1）RtkConfig.java：boolean开关默认false + 相关参数默认值
   例：enableAmbAnchor=false, ambAnchorMinFixCount=100, ambAnchorVar=1e-9

2）RtkOptimizations.java：独立静态类，所有优化逻辑封装于此
   - 每个方法首行检查开关：if (!cfg.enableXXX) { 原始行为/return; }
   - 开关关闭时行为与原版RTKLIB完全一致
   - 例：computeQScale() → if (!cfg.enableAdaptiveQ) { rtk.qScale=1.0; return; }

3）RtkCore.java：仅在关键调用点增加1行委托，不修改原有逻辑
   例1：RtkOptimizations.computeSnrMedian(rtk,...);  // 替代原snr计算
   例2：RtkOptimizations.computeQScale(rtk,...);      // udstate()后
   例3：RtkOptimizations.applyIggiii(rtk,...);        // ddres()后filter()前
   例4：ddidx() → if (cfg.enableParRefReselect) return RtkOptimizations.buildParIndex(...);

4）resamb_LAMBDA()中的模式：
   - enableParRefReselect：在ddidx()中切换双差索引构建策略
   - enableAmbAnchor：在resamb_LAMBDA()内分离锚固/自由模糊度子集，
     仅对自由子集执行LAMBDA搜索，锚固子集直接代入

所有新优化必须严格遵循此模式，确保：
  ✅ 开关默认false，关闭时与原版RTKLIB行为完全一致
  ✅ 新增逻辑封装在RtkOptimizations或新独立类中
  ✅ RtkCore仅增加if-branch委托，不修改原有代码行
  ✅ 侵入点用 // [OPT-XXX] 标注，便于RTKLIB版本升级时定位

2.1 逐级模糊度固定 EWL→WL→NL（P0 最高优先级）
─────────────────────────────────────────────────────────────────────
来源：      GREAT-PVT arsig 模块
目的：      利用多频波长差异逐级约束固定模糊度，提升RTK固定连续性和精度
现状短板：  仅单步窄巷LAMBDA+Ratio，多频利用率低
改造类型：  核心算法新增（逐级LAMBDA搜索）
依赖：      多频数据（≥3频），项目已支持NFREQ=6

逐级策略：
  EWL级：超宽巷（λ_EWL ≈ 0.86m），极易取整，Ratio阈值可放宽至1.5
  WL级： 宽巷（λ_WL ≈ 0.86m GPS L1/L2），受EWL约束后搜索空间缩小
  NL级： 窄巷（λ_NL ≈ 0.10m），受WL约束完成最终固定

与现有锚固机制的兼容：
  - EWL级：超宽巷极易取整，锚固意义不大，但仍需独立Ratio校验
  - WL级：宽巷固定结果约束NL，锚固可保护已稳定的WL模糊度
  - NL级：窄巷是最终精度，锚固最关键
  - 逐级AR的每一级都应支持锚固分离，但锚固计数仅在NL级管理
  - 注意：EWL/WL级虽然"极易取整"，但不能跳过验证，错误固定会污染NL级

【实现方法】
─────────────────────────────────────────────────────────────────────
1）RtkConfig新增开关和参数：
   public boolean enableCascadeAR = false;      // 总开关，默认关闭
   public double cascadeArRatioEwl = 1.5;       // EWL级Ratio阈值（放宽）
   public double cascadeArRatioWl = 2.0;        // WL级Ratio阈值
   public double cascadeArRatioNl = 3.0;        // NL级Ratio阈值（与thresar一致）
   public boolean cascadeArBootstrapping = false; // 逐级是否启用Bootstrapping

2）新增独立类 RtkOptimizationsCascadeAR.java（org.rtklib.java.rtkpos包）：
   - static int cascadeAmbFix(Rtk rtk, double[] bias, double[] xa,
                              int gps, int glo, int sbs, Nav nav)
   - 内部实现EWL→WL→NL三级LAMBDA搜索
   - 每级：构建双差模糊度子矩阵 → LAMBDA搜索 → Ratio/Bootstrapping校验
   - 上级固定结果作为约束代入下级（缩小搜索空间）
   - 每级均支持锚固分离（复用现有enableAmbAnchor逻辑）

3）RtkCore.resamb_LAMBDA()最小侵入修改：
   原代码：
     int nb = ddidx(rtk, ix, gps, glo, sbs);
     ... // 单步LAMBDA搜索
   修改为：
     if (rtk.rtkConfig.enableCascadeAR) {
         // [OPT-CASCADE-AR] 逐级模糊度固定
         return RtkOptimizationsCascadeAR.cascadeAmbFix(rtk, bias, xa, gps, glo, sbs, nav);
     }
     int nb = ddidx(rtk, ix, gps, glo, sbs);
     ... // 原有单步LAMBDA搜索不变

4）回退保证：
   - enableCascadeAR=false（默认）→ 完全跳过新代码，走原有resamb_LAMBDA逻辑
   - 与原版RTKLIB行为完全一致
   - 可随时通过开关A/B对照测试

分阶段落地：
  Phase 1：双频WL→NL（覆盖大多数双频接收机）
  Phase 2：三频EWL→WL→NL（完整三频逐级）

2.2 精细化残差编辑与周跳检测（P0，从P1提升）
─────────────────────────────────────────────────────────────────────
来源：      PRIDE redig 全套模块
目的：      通过残差时序迭代跳变检测等手段保障模糊度弧段连续
改造类型：  新增模块（弧段域质控）
优先级提升理由：所有高级AR策略的底层基础，周跳检测不可靠则逐级AR和Partial AR失效

现状短板：
  - udbias()中仅有基本周跳处理（LLI标记 + 几何距离跳变）
  - 缺少残差时序迭代检测
  - 缺少伪距-载波一致性校验
  - 缺少弧段完整性筛查

与IGGIII的关系：
  - enableIggiii：观测域降权抑制粗差（单历元）→ 已有，RtkCore中ddres后filter前调用
  - PRIDE残差编辑：弧段域检测周跳和异常（多历元时序）→ 新增
  - 两者作用层面不同，互补

【实现方法】
─────────────────────────────────────────────────────────────────────
1）RtkConfig新增开关和参数：
   public boolean enableResidualEdit = false;    // 总开关，默认关闭
   public double residEditJumpThresh = 4.0;      // 残差跳变阈值（σ倍数）
   public int residEditMinArcLen = 10;            // 最小弧段长度（历元数）
   public double residEditPcConsistThresh = 3.0;  // 伪距-载波一致性阈值

2）新增独立类 RtkOptimizationsResEdit.java（org.rtklib.java.rtkpos包）：
   - static void checkCycleSlip(Rtk rtk, double[] v, double[] R, int[] vflg, int nv)
     残差时序迭代跳变检测：对每个卫星-频率的残差序列检测突变
   - static void checkPcConsistency(Rtk rtk, Obsd[] obs, int[] sat, int ns, int nf)
     伪距-载波一致性校验：|P - L*λ| 超限则标记周跳
   - static void screenArcIntegrity(Rtk rtk)
     弧段完整性筛查：过短弧段或弧段内残差方差过大则重置模糊度
   - 每个方法首行：if (!cfg.enableResidualEdit) return;

3）RtkCore.udbias()最小侵入修改：
   原代码（udbias末尾，模糊度初始化/重置逻辑后）：
     // 原有周跳检测（LLI+几何距离跳变）
   修改为：
     // [OPT-RES-EDIT] 精细化残差编辑与周跳检测
     RtkOptimizationsResEdit.checkCycleSlip(rtk, v, R, vflg, nv);
     RtkOptimizationsResEdit.checkPcConsistency(rtk, obs, sat, ns, nf);
     RtkOptimizationsResEdit.screenArcIntegrity(rtk);
     // 原有周跳检测不变（作为兜底）

4）回退保证：
   - enableResidualEdit=false（默认）→ 完全跳过，udbias()行为与原版一致
   - 与现有enableIggiii互不干扰（不同调用点，不同作用域）

2.3 部分模糊度固定 Partial AR（P1）
─────────────────────────────────────────────────────────────────────
来源：      GREAT-PVT arsig 模块
目的：      全局Ratio失败后，剔除劣质模糊度维度，保留可信子集完成固定
改造类型：  核心算法新增（LAMBDA子集搜索）

与现有机制的关系：
  - enableAmbAnchor：保护"过去已稳定"的模糊度（向后保护）→ 互补，可叠加
  - enableParRefReselect：仅排除参考星，非真正子集选择 → 弱化版，保留作兜底
  - Partial AR：在当前历元"剔除当前劣质"维度（向前筛选）

安全约束：
  - 必须三判据联合校验：Ratio + Bootstrapping成功率 + 残差时序连续性
  - 缺一不可，否则假固定风险不可控
  - 测绘场景宁可失锁不输出错误解

【实现方法】
─────────────────────────────────────────────────────────────────────
1）RtkConfig新增开关和参数：
   public boolean enablePartialAR = false;       // 总开关，默认关闭
   public double partialArMinRatio = 2.0;        // 子集最小Ratio阈值
   public int partialArMinSats = 4;              // 子集最少卫星数
   public double partialArMinBootstrapping = 0.99; // 子集最小Bootstrapping成功率
   public int partialArMaxSubsetTries = 10;      // 最大子集尝试次数

2）新增独立类 RtkOptimizationsPartialAR.java（org.rtklib.java.rtkpos包）：
   - static int partialAmbFix(Rtk rtk, double[] bias, double[] xa,
                              int[] ix, int nb, int gps, int glo, int sbs)
   - 全局LAMBDA失败后调用
   - 策略：按模糊度方差排序，逐个剔除最大方差维度，对剩余子集重试LAMBDA
   - 每次子集固定需通过三判据：Ratio + Bootstrapping + 残差时序
   - 与enableAmbAnchor叠加：先锚固分离，再对自由子集做Partial AR

3）RtkCore.resamb_LAMBDA()最小侵入修改：
   原代码（LAMBDA搜索后Ratio检验失败处）：
     if (rtk.sol.ratio < rtk.sol.thres) {
         return -1;  // 固定失败
     }
   修改为：
     if (rtk.sol.ratio < rtk.sol.thres) {
         if (rtk.rtkConfig.enablePartialAR) {
             // [OPT-PARTIAL-AR] 部分模糊度固定
             int nbPar = RtkOptimizationsPartialAR.partialAmbFix(
                             rtk, bias, xa, ix, nb, gps, glo, sbs);
             if (nbPar > 1) return nbPar;
         }
         return -1;  // 固定失败
     }

4）回退保证：
   - enablePartialAR=false（默认）→ Ratio失败直接return -1，与原版一致
   - 与enableAmbAnchor独立：两者可分别开关、叠加使用

2.4 Bootstrapping成功率联合判据（P1，从P2提升）
─────────────────────────────────────────────────────────────────────
来源：      GREAT-PVT arsig 模块
目的：      作为Ratio的互补判据，与Ratio、残差时序联合判定模糊度固定可靠性
改造类型：  新增判据模块
优先级提升理由：Partial AR安全落地的必要条件，没有多判据保护就是"裸奔"

现状：
  - 单一Ratio判据，参数敏感性分析显示thresar从2.0→6.0 FIX率下降14.9%
  - Ratio判据对阈值敏感，需要互补判据降低敏感性

【实现方法】
─────────────────────────────────────────────────────────────────────
1）RtkConfig新增开关和参数：
   public boolean enableBootstrapping = false;    // 总开关，默认关闭
   public double bootstrappingMinSuccess = 0.99;  // 最小Bootstrapping成功率
   public boolean bootstrappingWithRatio = true;  // 是否与Ratio联合（true=双判据）

2）新增独立类 RtkOptimizationsBootstrap.java（org.rtklib.java.rtkpos包）：
   - static double computeSuccessRate(double[] a, double[] Q, int n)
     计算Bootstrapping成功率：对排序后的模糊度逐个取整，
     累积∏(1-2*Q_erfc(|a_i-round(a_i)|/σ_i))
   - static boolean validateFix(Rtk rtk, double[] bias, int nb)
     联合判据：Ratio检验 && Bootstrapping成功率 >= bootstrappingMinSuccess
   - 每个方法首行：if (!cfg.enableBootstrapping) return true;（默认通过）

3）RtkCore.resamb_LAMBDA()最小侵入修改：
   原代码（Ratio检验通过后）：
     if (rtk.sol.ratio >= rtk.sol.thres) {
         // 固定成功
     }
   修改为：
     if (rtk.sol.ratio >= rtk.sol.thres) {
         // [OPT-BOOTSTRAP] Bootstrapping联合判据
         if (!RtkOptimizationsBootstrap.validateFix(rtk, bias, nb)) {
             rtk.sol.ratio = 0.0f;  // 判据未通过，视为固定失败
             return -1;
         }
         // 固定成功
     }

4）回退保证：
   - enableBootstrapping=false（默认）→ validateFix()直接return true，仅用Ratio
   - 与原版RTKLIB行为完全一致
   - 可与Partial AR、逐级AR独立开关、叠加使用

2.6 GPT3+VMF3对流层模型（RTK场景降为P1/P2，PPP场景P0）
─────────────────────────────────────────────────────────────────────
来源：      PRIDE PPP-AR
目的：      提升中长基线RTK和PPP的对流层改正精度
改造类型：  新增模型替换

优先级调整理由：
  - 项目实测短基线（<10km）Saastamoinen FIX率81.0%，EST模式仅40.4%
  - GPT3+VMF3在短基线RTK收益有限
  - 真正价值在中长基线（>10km）和PPP
  - RTK场景降为P1/P2，PPP场景保持P0

工程量：需嵌入1°×1° GPT3网格数据和VMF3球谐系数，数据文件约数MB-数十MB

AOD数据下载：
  - VMF3需要AOD（.grib2或.netcdf格式的数值天气预报数据
  - 可通过ProductDownloader扩展支持AOD自动下载
  - 或使用GPT3纯经验模型（无需AOD，精度略降但仍优于GMF）

【实现方法】
─────────────────────────────────────────────────────────────────────
1）RtkConfig/PrcOpt新增开关：
   PrcOpt.tropoopt新增枚举值 TROPOOPT_GPT3VMF3（与现有SAASTAMOINEN/EST并列）
   无需额外boolean开关，通过tropoopt枚举切换即可

2）新增独立类 Gpt3Vmf3Model.java（org.rtklib.java.tropo包）：
   - static double[] gpt3(double[] pos, double mjd, Gpt3Grid grid)
     GPT3经验模型：计算压力、温度、水汽压、a_h/a_w等VMF3映射系数
   - static double vmf3(double el, double[] vmf3Coeff)
     VMF3映射函数：替代GMF/NMF
   - static double tropoDelayGpt3Vmf3(double[] pos, double el, double mjd, ...)
     完整对流层天顶延迟计算
   - Gpt3Grid：1°×1°网格数据加载类（从嵌入资源文件或外部文件读取）

3）RtkCore.tropo()最小侵入修改：
   原代码：
     if (opt.tropoopt == TROPOOPT_SAASTAMOINEN) { ... }
   修改为：
     if (opt.tropoopt == TROPOOPT_GPT3VMF3) {
         // [OPT-GPT3-VMF3] GPT3+VMF3对流层模型
         return Gpt3Vmf3Model.tropoDelayGpt3Vmf3(pos, el, mjd, ...);
     }
     if (opt.tropoopt == TROPOOPT_SAASTAMOINEN) { ... }  // 原有逻辑不变

4）回退保证：
   - tropoopt=SAASTAMOINEN（默认）→ 完全走原有对流层计算，与原版一致
   - 仅新增一个枚举值分支，不修改任何原有代码
   - GPT3网格数据按需加载，不使用时不占内存

2.7 自适应随机游走过程噪声（P2）
─────────────────────────────────────────────────────────────────────
来源：      PRIDE PPP-AR
目的：      按物理参数区分噪声模型，提升解算稳健性
改造类型：  过程噪声模型配置化

与现有enableAdaptiveQ的关系：
  - study方案：参数类型级（ZTD用随机游走、钟差用白噪声、位置不使用随机游走）
  - 现有enableAdaptiveQ：运动状态级（位置过程噪声缩放，静态压制/动态放大）
    → 已有，RtkCore.udstate()中：if (enableAdaptiveQ && qScale!=1.0) { qh*=qScale²; }
  - 两者互补，可叠加

【实现方法】
─────────────────────────────────────────────────────────────────────
1）RtkConfig新增开关和参数：
   public boolean enableParamTypeNoise = false;   // 总开关，默认关闭
   public double noiseZtdRw = 1e-4;               // ZTD随机游走过程噪声(m/√s)
   public double noiseClkWhite = 1e2;             // 钟差白噪声(m)
   public double noiseIonoRw = 1e-3;              // 电离层随机游走(m/√s)

2）新增方法 RtkOptimizations.applyParamTypeNoise()：
   - static void applyParamTypeNoise(Rtk rtk, double[] P, int nx, double tt)
   - 按状态索引区分参数类型，施加不同噪声模型：
     - 位置(0-2)：不使用随机游走（位置本身是状态，非时变参数）
     - ZTD(5)：随机游走 → P[i*nx+i] += noiseZtdRw² * |tt|
     - 钟差(6-8)：白噪声 → P[i*nx+i] = noiseClkWhite²（替换，非累加）
     - 模糊度(na..nx)：无过程噪声（保持不变）
   - 首行：if (!cfg.enableParamTypeNoise) return;

3）RtkCore.udstate()最小侵入修改：
   原代码（过程噪声矩阵Q构建后）：
     // 统一 prn[i]² * |tt| 过程噪声
   修改为：
     // [OPT-PARAM-NOISE] 参数类型级自适应过程噪声
     RtkOptimizations.applyParamTypeNoise(rtk, P, nx, tt);
     // 原有统一过程噪声逻辑不变（当enableParamTypeNoise=false时走原逻辑）

4）回退保证：
   - enableParamTypeNoise=false（默认）→ 完全跳过，走原有prn[i]²*|tt|逻辑
   - 与enableAdaptiveQ独立：两者可分别开关、叠加使用
   - enableAdaptiveQ管位置噪声缩放，enableParamTypeNoise管ZTD/钟差/电离层噪声类型

3. PPP阶段优化方案（RTK交付后启动）
================================================================================

【PPP侵入架构说明——与RTK的关键差异】
─────────────────────────────────────────────────────────────────────
RTK优化侵入模式：RtkCore + RtkOptimizations，1行委托即可扩展
PPP优化侵入模式：PppCore是final类，所有方法private static，无RtkOptimizations
等价扩展点。PPP优化需要更深的侵入，有两种策略：

策略A：仿RTK模式，新增PppOptimizations独立类 + PppCore最小侵入
  适用：对流层模型替换、潮汐模型升级、周跳检测增强
  侵入量：与RTK同级别，PppCore中增加if-branch委托
  示例：
    PppCore.udtrop_ppp()中：
      if (opt.tropoopt == TROPOOPT_GPT3VMF3) {
          // [OPT-GPT3-VMF3] GPT3+VMF3对流层模型
          return PppOptimizations.tropoDelayGpt3Vmf3(...);
      }

策略B：继承扩展PppCore，新增PppCoreEx子类
  适用：ISB/IFCB/IFB偏差估计、PPP-AR模糊度固定
  原因：这些优化需要扩展PPP状态向量维度、修改观测方程结构，
        无法通过1行委托实现，必须重写pppos/udstate_ppp/pppRes等核心方法
  侵入量：较大，需继承PppCore并override多个方法
  实现方案：
    public class PppCoreEx extends PppCore {
        @Override
        public static void ppos(Rtk rtk, Obsd[] obs, int n, Nav nav) {
            // 扩展状态向量（新增ISB/IFCB/IFB参数）
            int nx = pppnx(opt) + PppBiasModel.extraDim(cfg);
            // 调用super.ppos()或重写核心逻辑
        }
    }
  回退保证：
    PppProcessor中通过Config开关选择：
      if (cfg.enableIsbIfcbIfb || cfg.enablePppAR) {
          PppCoreEx.ppos(rtk, obs, n, nav);  // 扩展版
      } else {
          PppCore.ppos(rtk, obs, n, nav);     // 原版
      }
    开关全关时走原版PppCore，与原版RTKLIB行为完全一致

  注意：PppCore是final类，需先移除final修饰符（最小改动），
  或改用组合模式（PppCoreEx内委托PppCore而非继承）。
  推荐组合模式，避免修改PppCore类声明。

3.1 GPT3+VMF3对流层模型（PPP场景P0）

3.3 ISB/IFCB/IFB全维度偏差模型（P1）
─────────────────────────────────────────────────────────────────────
来源：      PRIDE PPP-AR
目的：      PPP非差解算中必须估计的偏差，提升多系统、多频高精度PPP精度
改造类型：  新增偏差参数估计
侵入策略：  策略B（需扩展PPP状态向量维度，侵入较大）

强约束：双差RTK天然抵消，禁止引入。如果在RTK中估计ISB/IFB，会引入冗余参数
降低FIX率。严格限定在PPP模块内实现。

【实现方法】
─────────────────────────────────────────────────────────────────────
1）PppConfig新增开关：
   public boolean enableIsbIfcbIfb = false;       // 总开关，默认关闭
   public boolean estimateIsb = true;             // 估计ISB（系统间偏差）
   public boolean estimateIfcb = true;            // 估计IFCB（频间码偏差）
   public boolean estimateIfb = true;             // 估计IFB（频间相位偏差）

2）新增独立类 PppBiasModel.java（org.rtklib.java.ppp包）：
   - static int extraDim(PppConfig cfg) → 返回新增状态维度
   - static void extendStateVector(Rtk rtk, int nx, PppConfig cfg)
     扩展x/P数组，初始化ISB/IFCB/IFB参数
   - static void extendObsEquation(...) → H矩阵新增对应列
   - RTK模块完全不调用此类（编译级隔离）

3）新增PppCoreEx.java（组合模式，不修改PppCore类声明）：
   public class PppCoreEx {
       public static void ppos(Rtk rtk, Obsd[] obs, int n, Nav nav, PppConfig cfg) {
           if (!cfg.enableIsbIfcbIfb) {
               PppCore.ppos(rtk, obs, n, nav);  // 委托原版
               return;
           }
           // 扩展版：扩展状态向量 + 修改观测方程
           int nx = PppCore.pppnx(opt) + PppBiasModel.extraDim(cfg);
           ... // 重写pppos核心逻辑（复用PppCore的辅助方法）
       }
   }

4）PppProcessor最小侵入修改：
   原代码：
     PppCore.ppos(rtk, obs, n, nav);
   修改为：
     // [OPT-ISB-IFCB] ISB/IFCB/IFB偏差模型
     if (cfg.enableIsbIfcbIfb) {
         PppCoreEx.ppos(rtk, obs, n, nav, cfg);
     } else {
         PppCore.ppos(rtk, obs, n, nav);
     }

5）回退保证：
   - enableIsbIfcbIfb=false（默认）→ 走原版PppCore.ppos()，与原版一致
   - PppCore类声明不修改（组合模式，非继承）
   - RTK模块完全不受影响（代码隔离）

实现方案：
- 独立Maven模块 rtklib-product（与rtklib-core、rtklib-adjust平级）
- 主类 org.rtklib.java.product.ProductDownloader
- 依赖：仅slf4j+logback，不依赖rtklib-core，零第三方依赖
- 输入：日期范围（起止年月日）、产品类型、本地缓存目录
- 输出：下载到本地的SP3/CLK/ERP/DCB文件路径
- 功能：
  1) 根据日期自动生成产品文件名和URL（支持IGS/WUM/CAS多分析中心）
  2) 多源URL自动切换（主源失败→备选源→实时产品）
  3) 本地缓存（已下载不重复下载，支持.gz/.Z自动解压）
  4) 跨日产品自动合并（跨日处理需合并前后两天的SP3/CLK）
  5) 进度显示和错误提示
- URL优先级（与PRIDE-PPPAR pdp3.sh一致）：
  1) bdspride.com（PRIDE主源，国内高速，FTPS→HTTPS）
  2) igs.ign.fr（IGS官方MGEX）
  3) igs.gnsswhu.cn（WHU镜像，国内备选）
  4) RTS实时产品（RAP失败后回退）
- 默认缓存目录：{user.dir}/product/（与PRIDE-PPPAR一致）
- 默认URL基础地址：可通过构造器配置覆盖
- 缓存目录结构（与PRIDE一致）：
    product/
    ├── orbit/     SP3精密轨道
    ├── clock/     CLK精密钟差
    ├── erp/       ERP地球自转参数
    ├── dcb/       DCB/BIA码偏差
    └── table/     ANTEX/leapsec等静态表文件
- 所有日期/时间均基于UTC：
  - 输入的LocalDate视为UTC日期（GPS时与UTC差≤18s，对按日产品无影响）
  - DOY（年积日）按UTC日计算
  - GPS周从1980-01-06(UTC)起算
  - IGS产品文件名中的YYYYDDD均为UTC日期
- 定位：独立辅助工具模块，不依赖rtklib-core，后续可移走独立为命令行工具
- 优先级：中（PPP测试前必须可用，RTK阶段不需要）
- 状态：✅ 已实现，16个单元测试全部通过

4.2 部分模糊度固定 Partial AR vs 现有
─────────────────────────────────────────────────────────────────────
维度        study.txt              项目现状
概念        全局Ratio失败后剔除     已有两套相关但不同的机制
            劣质维度保留可信子集
现有1       —                      enableAmbAnchor：锚固已稳定模糊度
现有2       —                      enableParRefReselect：LAMBDA失败时重选参考星

讨论：Partial AR与AmbAnchor互补而非替代：
  - AmbAnchor：保护"过去已稳定"的模糊度（向后保护）
  - Partial AR：在当前历元"剔除当前劣质"维度（向前筛选）
  - enableParRefReselect是Partial AR的弱化版本——只排除参考星，不剔除任意劣质维度

风险管控：Partial AR的假固定风险需要多判据联合校验（Ratio+Bootstrapping+残差时序），
当前项目仅有Ratio判据。必须配套实现Bootstrapping成功率判据，否则假固定风险不可控。

5. 关键风险与整改
================================================================================

5.1 Partial AR假固定风险（最高风险）
─────────────────────────────────────────────────────────────────────
收益风险同源。当前项目缺少多判据校验体系：

判据                  study要求    项目现状
─────────────────────────────────────────────────────────────────────
Ratio检验              ✅           ✅ 已有
Bootstrapping成功率    ✅           ❌ 缺失
残差时序连续性         ✅           ❌ 缺失

整改：Partial AR必须三判据联合，缺一不可。Bootstrapping从P2提升到与Partial AR
同批次实现。

5.2 优化项测试验证不足
─────────────────────────────────────────────────────────────────────
现有优化测试报告显示：所有优化项在高质量短基线数据上效果完全相同（FIX率94.5%无变化）。
说明：
  - 现有优化项缺少困难场景测试数据（城市峡谷、多路径、长基线）
  - study.txt的优化项同样需要困难场景验证
  - 参数敏感性分析仅覆盖基础PrcOpt参数，未覆盖RtkConfig优化项参数

建议建立分级测试体系：
  Level 1：高质量短基线（回归验证，确保不退化）
  Level 2：城市峡谷/多路径数据（验证IGGIII、Partial AR、周跳检测）
            需带IMU和不带IMU数据分别测试（GraphRTK-INS紧耦合备选）
  Level 3：中长基线（验证GPT3/VMF3、梯度参数、ISB/IFB）
  Level 4：PPP后处理（验证GPT3/VMF3、IERS2010、潮汐）

5.3 IGGIII参数默认值与文档不一致
─────────────────────────────────────────────────────────────────────
代码中RtkConfig.java的IGGIII默认值：
  iggiiiK0 = 3.0;   // 文档说1.5
  iggiiiK1 = 6.0;   // 文档说3.0
  iggiiiMinW = 0.5;  // 文档说1e-4

文档RTK_Extra_Optimizations.md中写的是K0=1.5, K1=3.0, minW=1e-4，这是标准IGGIII
参数。代码中的值偏宽松，可能导致抗差效果不足。

整改：统一为文档值，或明确说明代码值的选择依据。

5.4 逐级AR与现有锚固机制的兼容
─────────────────────────────────────────────────────────────────────
当前resamb_LAMBDA()已实现锚固/自由分离逻辑。逐级AR（EWL→WL→NL）需要在每一级
都执行LAMBDA搜索，与锚固分离的交互需要仔细设计。

关键注意：EWL和WL的固定结果本身也是整数，如果EWL/WL级出现错误固定，会污染NL级
的搜索。所以EWL/WL级虽然"锚固意义不大"，但仍需要独立的Ratio或Bootstrapping校验，
不能因为"极易取整"就跳过验证。

7. 回退安全与维护架构
================================================================================

7.1 回退安全设计原则
─────────────────────────────────────────────────────────────────────
1）所有优化通过独立Config开关控制，默认关闭
2）开关关闭时与原版RTKLIB行为完全一致（代码级保证，非配置级）
3）支持独立回退和A/B对照测试
4）新旧算法互补叠加，不替换

7.2 侵入点最小化策略（遵循现有模式）
─────────────────────────────────────────────────────────────────────
现有项目已建立成熟的侵入模式，所有新优化严格遵循：

模式A：Config开关 + RtkOptimizations独立类 + RtkCore 1行委托
  适用：逐级AR、周跳检测、Partial AR、Bootstrapping、BDS码偏差、过程噪声
  示例（现有）：
    RtkCore.relpos()中：
      RtkOptimizations.computeSnrMedian(rtk,...);    // 1行委托
      RtkOptimizations.computeQScale(rtk,...);        // 1行委托
      RtkOptimizations.applyIggiii(rtk,...);          // 1行委托
    RtkCore.ddidx()中：
      if (cfg.enableParRefReselect) return RtkOptimizations.buildParIndex(...);  // if-branch
  新增优化同模式：
    if (cfg.enableCascadeAR) return RtkOptimizationsCascadeAR.cascadeAmbFix(...);
    if (cfg.enablePartialAR) { ... RtkOptimizationsPartialAR.partialAmbFix(...); }
    if (!RtkOptimizationsBootstrap.validateFix(...)) return -1;

模式B：枚举值扩展 + 新增独立类 + 调用点if-branch
  适用：GPT3+VMF3（tropoopt枚举）、IERS2010（tideopt枚举）
  示例：
    if (opt.tropoopt == TROPOOPT_GPT3VMF3) return Gpt3Vmf3Model.tropoDelay(...);
    if (opt.tideopt == TIDEOPT_IERS2010) return Tides.tideDisplacementIers2010(...);

关键约束：
  ✅ RtkCore仅增加if-branch委托，不修改任何原有代码行
  ✅ 新增逻辑全部封装在独立类中（RtkOptimizations*或新包）
  ✅ 每个方法首行检查开关，关闭时return原始行为
  ✅ 侵入点用 // [OPT-XXX] 标注

模式C：组合模式扩展PppCore（PPP策略B专用）
  适用：ISB/IFCB/IFB偏差估计、PPP-AR模糊度固定
  原因：需扩展PPP状态向量维度/修改观测方程结构，无法1行委托
  方案：新增PppCoreEx（组合模式），内委托PppCore
    public class PppCoreEx {
        public static void ppos(Rtk rtk, Obsd[] obs, int n, Nav nav, PppConfig cfg) {
            if (!cfg.enableIsbIfcbIfb && !cfg.enablePppAR) {
                PppCore.ppos(rtk, obs, n, nav);  // 委托原版
                return;
            }
            // 扩展版逻辑
        }
    }
  PppProcessor中：
    if (cfg.enableIsbIfcbIfb || cfg.enablePppAR) PppCoreEx.ppos(...)
    else PppCore.ppos(...)
  关键：不修改PppCore类声明（保持final），用组合而非继承
  回退：开关全关→走原版PppCore.ppos()，与原版RTKLIB一致

9. 总结
================================================================================

study.txt的优化方案方向正确、场景边界清晰、风险意识强，经交叉审核后主要修订：

1）周跳检测优先级过低：从P1提升到P0，它是所有AR策略生效的前提
2）Bootstrapping与Partial AR脱节：必须同步实现，否则Partial AR假固定风险不可控
3）GPT3/VMF3对RTK收益夸大：短基线RTK收益有限，区分RTK/PPP优先级
4）缺少困难场景测试：现有测试数据过于理想，无法验证优化项实际效果
5）IGGIII参数代码与文档不一致：需统一或说明依据
6）未覆盖项目现有独有优化：atmFrozenNsThresh、enableSnrMedian、BaseStationMonitor
   应明确纳入整体规划
7）精密产品下载模块已实现：rtklib-product独立模块，16个测试通过
